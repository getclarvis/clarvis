# Selectable E2E journeys

Use these operator-facing choices without requiring knowledge of internal scenario IDs:

| Profile                    | What to execute                                                                                                                                    |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| Happy paths                | The happy-path column below, on the selected provider and available test integrations                                                              |
| Happy plus secondary flows | Happy paths plus the secondary column: cancellation, validation, recovery and navigation interruptions                                             |
| Specific flows             | Only the named journeys/subcases and prerequisites; accept feature names or matrix IDs                                                             |
| Entire app                 | [Full audit](full-audit.md): every matrix scenario, failures/races, performance, integrations and native-platform requirements, with explicit gaps |

Use the already requested choice. For an unspecified broad E2E request ask once, suggesting happy
plus secondary flows for routine product validation. Do not require another scope confirmation
when the operator has already said “entire app” or named a defect. Performance-only work goes
directly to [performance.md](performance.md).

These profiles select subcases of [coverage-matrix.md](coverage-matrix.md); they do not replace its
minimum proof or turn a happy subcase into a pass for the entire parent row. Report selected subcases
as such and mark other subcases out of scope. In an entire-app audit every matrix ID needs a verdict.
In narrower profiles only selected IDs/subcases need ledger rows. Unavailable selected integrations
remain blocked/unverified; do not silently omit them or broaden to unrelated accounts.

Cross-platform, physical-terminal, exhaustive races/security and performance soak belong to the
entire-app profile unless explicitly requested in a narrower scope. A deterministic MCP/SSH
fixture proves its controlled boundary; it is not a real external-service pass.

## Evidence and stopping

Group compatible journeys around one fixture and build. Keep separate assertions even when one
run proves tools, diff, transcript and session persistence. A happy-only report must say it did
not execute secondary cases. Use the ledger shape in [report-template.md](report-template.md)
for broad runs; a selected regression can use a compact equivalent.

Stop repeated provider attempts after the same authentication or entitlement failure; request
the missing input while continuing independent work. Stop on live-state mutation or secret exposure,
clean up and report it. For ordinary product failures capture reproduction and recovery, then
continue independent selected journeys. Report defects rather than silently turning a test request
into an unlimited repair project. Scope/time/cost exhaustion leaves remaining requirements
unverified, never passed.
